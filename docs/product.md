# 产品体验与比较规则

Arc'teryx Deal Sentinel 希望帮助用户完成三个决定：**现在有什么值得看，指定规格哪里更便宜，何时值得行动。** 本文说明已确定的产品方向；当前实现进展以 [首页状态表](../README.md#当前进展) 为准。

## 浏览不同款式

进入管理台即可浏览商品图片、名称、颜色、尺码与最低 EUR 报价。首页以款式聚合信息，默认按相对德国官网原价的节省比例降序排列。

同名商品仍需区分版本、性别及型号。颜色与尺码收在商品之下，避免同一款式的多个规格占满首页。用户设置全局尺码后，展示价格与排名跟随该尺码变化。

## 确认一件商品的购买机会

点开商品后，选择允许的颜色和尺码，比较对应规格在不同渠道的报价、库存与核实时间。每条结果保留商家及市场信息，并提供原始商品页面作为核查入口。

| 比较事项 | 产品规则 |
| --- | --- |
| 商品身份 | 型号、版本、性别、颜色与尺码匹配后，才作为同规格比较。名称相似仅能作为查找线索。 |
| 价格单位 | 统一展示 EUR，同时保留原币价格和所用汇率时间。 |
| 节省基准 | 使用德国官网同款的可核实原价；无法核实时不计算节省比例。 |
| 最低价 | 从所选渠道中符合规格、有效期和有货条件的最新报价里选取。 |
| 未指定规格 | 展示最低起价，并说明该价格对应的颜色和尺码。 |
| 未知或历史信息 | 未知值留空；历史价格、缺货报价与待核实信息不占据当前有货最低价。 |
| 价格条件 | 会员价、优惠码和其他限制需明确标注。当前商品比价不包含运费、额外税费和支付手续费。 |

节省比例的统一计算方式为：

**（德国官网同款原价 − 最低 EUR 报价）÷ 德国官网同款原价**

例如，若德国官网同款原价为 €300，符合条件的某渠道报价折合 €60，则相对德国官网节省 80%。这是说明规则的假设示例，并非实际商品优惠。

## 关注自己的价格条件

计划支持最高 EUR 价格和目标节省比例两种关注方式，并结合商品版本、允许颜色、尺码和商家共同判断。任一接入渠道出现符合条件的有效报价，即可进入提醒流程。

统一通知网关将用于接入后续配置的消息渠道。提醒内容计划包含商品、规格、报价、节省比例、核实时间及购买入口。具体通知通道尚未配置，完整提醒服务仍待建设与验证。

## 正在为自动下单做好准备

预授权自动购买的产品规则已明确：用户事先设定商品版本、允许颜色与尺码、商家范围、目标价格或节省比例、数量和最高结账预算。是否启用购买执行与是否接收提醒分别控制。

目标是任一允许渠道出现达标的有效报价后，提醒和购买流程并行启动，不等待其他渠道完成本轮检查，也不等待用户先读到通知。当前处于产品规则与流程准备阶段，商家结账适配和执行器仍待实现、验证。

真正执行购买时，需再次核对规格、库存和最终结账总额；最终付款范围还包括商家实际收取的运费、税费等项目。需要用户完成的验证应明确提示，订单只有获得商家确认后才能标记为成功。

自动下单目前未实现。当前阶段没有开放购买执行，也不会自动付款。

## 看清覆盖与时效

**秒级读取商品数据，真实变更时效验证中。** 2026-09-07 德国官方 Outlet 男装的一组有限实测取得 101 款商品、1,183 个规格；首轮列表与详情读取约 2.06 秒，随后 8 轮商品列表检查平均请求耗时约 1.22 秒。这些数字仅衡量读取返回数据的耗时，不能证明实时库存，也不是从商家改变价格到系统发现或用户收到提醒的延迟。

同批详情响应出现约 55 分钟的 HTTP 缓存年龄，不代表商品信息一定错误，但意味着快速取得的响应可能较早生成。时效验证需要确认实际出现的价格、库存变化何时可见，以及系统何时发现和展示；这部分尚无完整实测结论。

管理台计划同时展示已覆盖渠道和最近核实时间，使用户知道一次比较实际包含哪些来源。渠道数量、记录数量与具体规格的有效报价数量分别呈现。

商品报价、库存、汇率的时间分别保留。网络检查成功说明系统完成了一次检查；只有取得相应证据，才更新报价状态。某个渠道暂时不可用时，保留其历史记录并明确状态。

速度优化围绕可用的新信息展开：缩短从报价发现、规格核实到管理台展示与提醒的等待，同时持续检查已接入商品。当前尚无覆盖全部渠道的全天候服务验收结论，也不提供全网覆盖或固定库存更新时间承诺。
